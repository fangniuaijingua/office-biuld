# 项目 README 覆盖与扩展

用于“整理 README”“补全项目介绍”“项目说明太短”“突出一个主线但保留细节”等任务。目标是**重组并扩展**已确认的信息，而不是把项目改写成一段泛化简介。

## 1. 先收集，不先改写

将以下来源逐项列入覆盖台账：

- 当前 README、历史 README、旧分支 README 与用户贴出的原说明；
- 用户提供的截图、报告、视频说明和后续纠正；
- 目录树、包清单、源码入口、launch/CLI、配置文件、数据文件、LFS/Release 资产；
- 已经存在的模块说明、协议页和 `docs/` 页面。

不要因为一条新消息说“核心是 X”就丢掉此前已经确认的 Y。先区分：`核心主线`、`支撑模块`、`扩展实验`、`附加数据`、`历史/待验证`。

## 2. 建立覆盖台账

在工作笔记或 `docs/` 草稿中使用此表，直到每行都有去向：

| 来源要点 | 证据锚点 | 项目角色 | 目标页面与章节 | 动作 | 状态 |
| --- | --- | --- | --- | --- | --- |
| 示例：`racecar_navigation.launch` | `launch/racecar_navigation.launch` | 核心主线 | 根 README / 导航 | 根 README 保留 | 源码已核对 |
| 示例：完整 planner 参数 | `config/navigation/*.yaml` | 支撑模块 | `docs/navigation.md` | 移入子页并链接 | 源码已核对 |
| 示例：用户确认的现场集成 | 用户说明 + 现场记录 | 系统结果 | 根 README 摘要 + 集成页 | 纠正后保留 | 用户确认 |

动作只能是：`根 README 保留`、`移入子页并链接`、`纠正后保留`、`明确删除`。`明确删除`必须写明理由；“README 需要简洁”不是理由。

## 3. 根 README 的详细但可读结构

对有多个模块的技术项目，优先使用以下结构并按材料增减：

1. **一句话目标**：项目实际解决的任务，不写简历、宣传或泛化口号；
2. **项目范围与主链路**：用流程图或编号流程说明输入、关键转换、输出和控制闭环；
3. **主要功能/模块**：每个模块写职责、关键文件/命令、与主链路的关系；
4. **运行记录或截图**：说明截图展示什么、不证明什么；
5. **目录、数据与资源关系**：让读者知道资源属于哪个项目、是否为输入、是否需转换；
6. **构建、运行和验证入口**：可复制的最小命令及所需前提；
7. **范围、证据与限制**：区分源码可核对、用户确认和未包含内容；
8. **详细页导航**：参数、接口、实验、数据格式或集成记录过长时，放入 `docs/` 并从此链接。

“详细”不等于把所有代码粘进根 README。根页面要让读者理解每个已确认模块的存在和作用；子页负责完整参数表、函数链、格式细节、日志和图集。

## 4. 主线重定向时的保留规则

用户纠正项目主线后：

1. 更新标题、摘要、主链路和章节顺序；
2. 将原先被误放在主线的内容标为支撑/扩展/附加数据；
3. 保留仍与项目有关的模块说明，或移入子页并从根 README 链接；
4. 只有确认与项目无关时才迁移到正确仓库，并同步修复两侧说明；
5. 对“用户确认的集成结果”标明来源，不把它伪装成当前仓库源码已经完整复现的结果。

例如，导航项目的核心可以是“目标点自动到达”，但 URDF、传感器、里程计、地图、定位、局部规划器、控制指令转换和界面仍是可读的支撑模块；不能因为标题改为“导航”就删除它们。

## 5. 交付前覆盖审计

在 Markdown 格式检查之外，逐项复核覆盖台账：

- 每个来源要点是否已保留、正确下沉并链接，或有明确删除理由；
- 用户后续补充是否更新了原有章节，而非只在末尾附加一段；
- 标题、摘要、流程图、目录、截图说明、运行命令和限制是否一致；
- 根 README 是否仍能导航到详细模块页；
- 是否误把“突出主线”做成“删除支撑模块”。

交付中简要报告：覆盖条目数、根 README 保留数、下沉链接数、纠正数、明确删除数及其理由。未经用户同意，不把项目“简历化”或把简历描述写入项目文件。
