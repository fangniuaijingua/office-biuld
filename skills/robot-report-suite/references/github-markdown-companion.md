# GitHub Markdown 伴随文档

## 1. 目标与边界

当正式 `.docx/.pdf` 报告还需要在 GitHub 供队友、评审或复现者阅读时，使用“双载体”：

- **Word/PDF**：正式格式、模板页、完整论证、签字/封面、详细表格和可编辑交付；
- **Markdown**：仓库入口、快速理解、源码/图/日志导航、关键事实和证据边界；
- **共用源**：参数、图源、照片、日志摘要、证据状态和结论限制只维护一份事实清单。

Markdown 不是 DOCX 的逐页导出。它需要按屏幕阅读重组，但不能改变任何技术结论。

## 2. 选择仓库位置

先服从仓库既有目录约定；没有约定时使用：

```text
README.md                         # 项目总入口：只放一段定位与各子系统链接
docs/reports/<report-slug>/
  README.md                       # 报告导读、关键图、导航、证据状态
  <report-slug>.pdf               # 已通过格式审计的正式阅读版
  evidence-index.md               # 日志/照片/数据/代码版本索引
  figures/                        # 本报告引用的导出 SVG/PNG
```

不要把报告工作区、模板副本、临时渲染页、原始大视频或机密日志直接放进仓库。公开视频用 Release 或 LFS；在 Markdown 中放稳定链接、摘要和 SHA-256。`report-workspace/repo-companion/` 是发布前的暂存区，确认后才拷入仓库路径。

## 3. 内容映射与允许重复

每个事实建立 `sections/content-map.md`，最小字段：

| 内容单元 | 正式报告位置 | Markdown 位置 | 证据来源 | 状态 | 重复理由 |
| --- | --- | --- | --- | --- | --- |
| 项目目标/边界 | 摘要、绪论 | 导读开头 | 赛题/用户确认 | 用户确认 | 让仓库读者不必先下载 PDF |
| 关键接口/引脚 | 系统设计 | 模块 README | 源码、原理图 | 已核对 | 便于维护与复现 |
| 测试结论 | 测试章节 | 证据索引摘要 | 日志、数据、视频 | 实测/待验证 | 让浏览者了解验证范围 |
| 局限与待办 | 结论 | “限制与下一步” | 问题台账 | 待验证 | 避免 README 过度承诺 |

允许为不同阅读场景重复项目摘要、接口约束、危险边界、重要参数、结论限制；重复版本应改变信息密度和上下文，不得只是同一段换词。参数、单位、版本号、图号和证据状态必须一致。

## 4. GitHub 可读性规则

1. 采用标准 GitHub Flavored Markdown：一级标题每页仅一个，二/三级标题按逻辑递进；不要跳级。
2. 使用仓库相对路径，例如 `../docs/实施基线.md`、`figures/car-platform.jpg`；提交前逐个检查目标存在。
3. 图片必须有准确 `alt`；实物照片只说明可见装配/场景，不能单独证明性能。宽图可用简洁 HTML `img`，但关键内容不可只依赖 HTML 才能阅读。
4. 表格仅放适合窄屏阅读的字段；复杂参数表拆为“摘要表 + PDF/明细链接”，避免极宽表格和单元格长段落。
5. 代码、命令、帧格式和寄存器值使用带语言标记的 fenced code block；不把大段编译输出、二进制或截图文本塞进正文。
6. 所有测试性句子显式写明 `实测证据`、`用户确认`、`设计示意` 或 `待验证`；不要以图标、颜色或宣传语暗示结论。
7. 文风以项目真实术语、具体条件、已知限制和自然长短句为主。避免“本文将”“显著提升”“全面赋能”“综上所述”等无证据套话；可保留团队的自然技术笔记，但需修正歧义、单位和冲突。

## 5. README 的建议骨架

不要对所有项目强制同一章节。以下仅是机器人/嵌入式项目常用的最小骨架，按材料删改或重排：

```markdown
# 项目或子系统名称

一句定位：硬件/固件范围、当前版本和最关键的边界。

## 实物或任务示意
一至两张有图注、有来源状态的图片。

## 当前实现与职责
用短段落或表格说明本模块做什么、不做什么、与其他端如何交接。

## 关键实现
从真实难点中选择：控制、通信、硬件资源、标定或安全策略；链接到源码和设计图。

## 验证证据与限制
测试条件、已保存证据、未验证项、复现前置条件。

## 正式报告与材料索引
PDF、证据索引、图源、关联模块和版本信息。
```

项目处在设计阶段时，应以“设计取舍、接口合同、待验证清单”为核心；有完整实测数据时，再使用“条件—方法—结果—限制”结构。不要虚构曲线、时长、成功率或验收结论。

## 6. 双载体发布门

发布前逐项确认：

| 检查项 | Word/PDF | GitHub Markdown |
| --- | --- | --- |
| 事实、参数、单位与版本 | 与证据台账一致 | 与正式报告一致 |
| 图表 | 有源文件、图题、编号、证据状态 | 相对路径可打开、`alt` 与图注准确 |
| 结论 | 已测/待测边界清晰 | 不夸大、不比报告更强 |
| 格式 | 模板锚点、页眉、页数、渲染通过 | 标题、链接、表格、代码块经 GitHub 渲染复查 |
| 可追溯性 | 输出版本与模板/证据可定位 | PDF、源码、日志和材料入口可定位 |

任何一侧新增或更正参数、图片、结果、限制时，都回到内容映射，更新受影响的另一侧，再重新进行两种渲染检查。
