# GitHub Markdown 独立工作流

适用于没有正式 Word/PDF 交付的项目仓库：README、模块说明、通信协议、证据索引、开发历史、复盘和资料导航。它不是把仓库写成实验报告，也不为了“完整”补造未发生的测试或文档。

## 0. 先做仓库与分支预检

不要只根据当前检出的 `main`、截图或用户记忆判断项目内容。编辑前在目标仓库执行：

```powershell
git status --short --branch
git fetch origin --prune
git remote set-head origin -a
git branch -a -vv
git log --all --oneline --decorate -12
git ls-tree -r --name-only HEAD
git lfs ls-files
```

将以下信息写入工作笔记或事实台账：目标远程、GitHub 默认分支、实际包含源码/资料的分支、当前编辑分支、未提交改动、LFS/Release 资产以及准备修改的页面。`main`、`master` 或其他分支历史无关时，不能直接合并、强推、删除或改写默认分支；只有用户明确指定后才做这些远程分支操作。

若源码或资料只在 LFS 归档中，先记录对象名和大小。仅在确实需要核对内容且用户允许下载大文件时运行 `git lfs pull`；不能把未下载的归档推断成不存在的代码，也不能把归档内未核对的脚本写成已验证事实。

提交与推送是两项独立操作：用户只要求“提交”时，创建本地提交但不推送；只有明确要求“推送 / 发布 / 同步远程”时才写入远程。推送完成后执行：

```powershell
git fetch origin --prune
git remote set-head origin -a
python "<skill-dir>\scripts\check_github_markdown.py" "<repo-root>" `
  --strict --require-code-language --verify-git-state `
  --verify-remote-default --require-clean-tree
```

## 1. 先判定页面职责

先查看仓库现有结构、相邻模块和链接约定，再为本次页面选择一种主要职责：

| 页面 | 读者首先要得到什么 | 不应承载什么 |
| --- | --- | --- |
| 根 `README.md` | 项目范围、当前状态、子系统入口 | 全部实现细节与长日志 |
| 模块 `README.md` | 模块职责、接口、源码入口、限制 | 其他队员模块的重复说明 |
| 协议页 | 帧格式、时序、坐标/单位、异常边界 | 未经核对的抓包结论 |
| 证据索引 | 证据位置、版本、条件、公开边界 | 把截图当作性能结论 |
| 开发历史 | 决策、阶段变化与可追溯锚点 | 倒推出来的精确日期 |
| 复盘 | 问题、错误路径、修正与适用范围 | 归咎个人或宣传式总结 |

一个页面可以链接到其他页面，但不要让根 README 复制所有子页。若页面职责改变，先调整导航与链接，再移动正文。

## 2. 建立最小事实台账

在编辑前于项目的 `docs/` 或工作笔记中建立台账；它是事实来源，不一定需要公开发布：

| 事实/结论 | 阶段或条件 | 责任边界 | 证据位置 | 状态 | 公开限制 |
| --- | --- | --- | --- | --- |
| 示例：协议帧长度 | 固件版本 X | 定义与发送：A；接收验证：B | 源码路径、串口日志 | 源码/日志已核对 | 可公开 |

可用状态为：`实测证据`、`源码/日志已核对`、`用户确认`、`阶段记录`、`待验证`。不要把“设计意图”写成“实测证据”；一次照片只能说明可见装配或场景，不能单独证明性能。

用户的回忆、旧 README、截图与当前代码或训练日志冲突时，保留各自来源和阶段，不自行折中成一个数值。例如“约 400 轮训练”与旧说明中的“450 轮以上”不能合并成“训练约 400–450 轮并已提升精度”；没有原始结果文件时，只写为带来源的阶段记录，并明确最终指标待验证。

多人项目应按**阶段和交付边界**归属：例如“先完成模型部署与训练”“随后完成推理优化与帧率复测”是两个事实，不能压缩成笼统的“视觉由某人完成”。没有证据时使用中性表述并标为待确认。

## 2.1 项目介绍必须先做覆盖台账

当任务是重写、精简、扩充或“更适合展示”的项目 README 时，先阅读 [项目 README 覆盖与扩展](project-readme-coverage.md)。页面职责控制信息密度，**不**允许把已核对的技术要点静默删掉。

在编辑前为下列每一项建立一行覆盖台账：旧 README 的标题/段落/表格、用户贴出的说明、报告图片图注、源码入口、launch/命令、配置参数、数据文件和用户随后补充的更正。每行必须选择一个处理结果：

- `根 README 保留`：读者必须先理解的主链路与关键模块；
- `移入子页并从根 README 链接`：详细参数、完整接口表、长日志或附加模块；
- `纠正后保留`：原说明名称、路径或事实有误，但项目语义仍有效；
- `明确删除`：仅限重复、无关、敏感、过时或用户明确不要的内容，并记录删除理由。

未填处理结果的条目不能在改写后消失。用户说“核心是导航”“核心是感知”时，应调整信息的**优先级和标题**，而不是删除为该主线服务的仿真、建图、定位、控制、界面、数据或启动入口。若根 README 过长，创建 `docs/` 详细页并保留摘要和入口链接；不要以压缩篇幅代替信息架构。

## 3. 时间线与复盘

开发史分别标明：

- **精确记录**：提交、日志、照片或文档具有可复核时间戳；
- **阶段记录**：多个来源只能确认一个时间段；
- **回忆补充**：用户叙述重要但没有原始时间戳，保留为阶段描述。

复盘应使用“背景/错误假设 → 观察到的现象 → 修正动作 → 后续边界”的闭环。保留失败路线及其适用范围，比把过程改写成连续成功更能帮助后续使用者。

## 4. 浏览结构与 GitHub 格式

1. 每页只有一个一级标题，标题不跳级；标题文本使用稳定、可读的中文或英文，避免为锚点而频繁改名。
2. 页面较长（约 180 行以上，或有 6 个以上二级章节）时，在前部提供“目录”或“快速导航”；根 README 提供子页入口。
3. 将旧版本日志、完整引脚矩阵、排障细节等辅助内容放入 `<details>`，但不要折叠关键结论、安全边界、接口定义或测试限制。
4. 表格只保留适合窄屏阅读的字段；复杂矩阵拆成摘要表和明细页。使用仓库相对路径，不出现盘符开头的本机路径、文件 URI 或其他本机绝对路径。
5. 图片写准确 `alt` 和图注；视频、原始大日志和大二进制放 Release 或 LFS，在页面中提供稳定链接、简短说明和 SHA-256（如适用）。
6. 写作优先写具体锚点：文件、版本、参数、坐标系、测试条件、日期、接口或限制。删除只有形容词、没有可核对对象的段落；允许真实技术笔记的自然语气，但修正歧义、单位和冲突。
7. 项目 README 至少让读者找到：项目目标、端到端主链路、关键模块与源码/启动入口、运行或复现入口、数据/资源关系、已验证范围与限制。完整参数、模块细节和额外实验可下沉到 `docs/`，但根 README 必须保留它们的职责摘要和链接。

## 5. 发布门

编辑完成后运行：

```powershell
python "<skill-dir>\scripts\check_github_markdown.py" "<repo-root>" --strict --require-code-language --verify-git-state
```

它检查本地相对链接、图片 `alt`、一级标题、标题层级、可解析的页面锚点、绝对本机路径、长文档导航、过宽表格、代码块语言标记以及 Git diff 的空白错误。通过后仍要按事实台账复核证据状态，并在 GitHub 页面复查图片、折叠区、视频/PDF 链接与窄屏表格。远程发布后追加 `--verify-remote-default --require-clean-tree`，核对远程默认分支与本地跟踪状态。

独立 Markdown 交付只报告：修改文件、各页职责、事实/归属台账摘要、检查结果、公开材料边界和待补证据。若后来新增正式 Word/PDF，再转入 [双载体伴随文档](github-markdown-companion.md) 建立内容映射；不要反向宣称已有 Markdown 等于正式报告。
